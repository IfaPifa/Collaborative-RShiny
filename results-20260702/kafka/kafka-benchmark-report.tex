\section*{Validity Notes (read first)}
% ------------------------------------------------------------------
\addcontentsline{toc}{section}{Validity Notes}

\begin{itemize}
  \item \textbf{Throughput (test 04) is excluded.} Across the 5 runs its p95
        rose monotonically (5.8\,s\,$\to$\,52.4\,s) and error rate rose
        5\%\,$\to$\,30\%, because the server was not reset between runs. The
        runs are serially contaminated, not independent, so the test is not
        reported here.
  \item \textbf{Latency tests lack a per-VU breakdown.} Tests 01, 02, 03 and
        08 ramp virtual users but tag metrics only with \texttt{app\_name},
        not \texttt{vu\_bucket}. Their avg/median/p95 therefore aggregate all
        load levels together: \emph{the median reflects low-VU samples while
        the p95 reflects high-VU samples}. Read median as the typical case and
        p95 as the loaded tail, not as a single operating point.
  \item \textbf{Per-app thresholds are baseline-calibrated} (10$\times$ each
        app's single-user baseline). A PASS means the app stayed within its
        own expected envelope under load, \emph{not} that it was fast in
        absolute terms.
\end{itemize}

\begin{tabular}{@{}lrr@{}}

\bottomrule
\end{tabular}

\medskip
\noindent The POST is $\approx$\,7\,ms regardless of app. The entire latency
difference between apps lives in the POLL, i.e.\ in how long each app's R code
takes to run. Kafka is not the bottleneck for the heavy apps; their own
computation is.

\section{Analysis}
% ------------------------------------------------------------------

The Kafka architecture is correct and stable on every reliability dimension:
zero data loss, zero cross-contamination, zero lifecycle errors, across all
five runs. Persistence (save/restore) and presence (WebSocket) are uniformly
fast.

The collaboration-path latency splits the apps cleanly into two groups. Six
apps (Calculator, Geospatial, DataExchange, MonteCarlo, Advanced,
ClimateAnomaly) relay in $\approx$\,265\,ms. Two apps (Analytics, MLTrainer)
sit near 10\,s on relay and higher on multi-user. The transport/computation
decomposition (\S\ref{sec:postpoll}) shows the POST into Kafka is $\approx$\,7\,ms
for every app; the difference is entirely in the POLL, i.e.\ the time each
app's R backend needs to compute its result. \textbf{For Analytics and
MLTrainer this latency is intrinsic to the application, not a property of
Kafka.}

\paragraph{Open question for the next experiment.} Because all apps currently
share consumer infrastructure, a heavy app's long computation may
head-of-line block lighter apps under concurrency. Whether per-app topic
partitioning with key-based routing isolates that effect is the subject of the
planned follow-up run. It is an \emph{isolation-under-concurrency} question;
it will not (and is not expected to) reduce the heavy apps' own compute time.

\paragraph{Caveats.} (1) Throughput is excluded as invalid. (2) Latency tests
aggregate across VU levels because they are not VU-tagged; a future run should
tag tests 01/02/03/08 with \texttt{vu\_bucket} to recover latency-vs-load
curves for the collaboration path.
